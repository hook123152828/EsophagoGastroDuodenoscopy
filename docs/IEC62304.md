## 1. 軟體安全分類（條款 4.3）

**分類結果：Class B — 可能造成非嚴重傷害。**

理由：

本系統對上消化道內視鏡影片提供三類輔助標註——解剖部位、腸上皮化生（IM）分割、
息肉偵測與分割。它**不控制任何硬體、不改變檢查流程、不產生診斷結論**，
所有輸出都疊在既有影像上供醫師判讀。因此不屬於 Class C。

但它也不是 Class A。Class A 的前提是「不可能造成傷害」，而本系統：

- 畫面上直接寫出 `IM score 2 · 50.0%` 這類具體判讀，具有明確的暗示性
- 部位覆蓋清單會標示某部位「seen」，可能讓使用者誤以為該部位已充分檢查
- 偽陰性（漏標病灶）可能造成延誤診斷，屬非嚴重但真實的傷害路徑

依 62304 的風險決策樹，在**「無外部風險控制措施可將傷害降至可忽略」**的前提下，
上述傷害路徑成立，故分類為 **Class B**。

> 本分類假設使用情境為「醫師全程在場並自行判讀」。若未來改為非同步判讀或
> 用於篩檢決策，需重新分類。

## 3. 軟體需求（條款 5.2）

需求以介面契約的形式定義於 [`PROTOCOL.md`](PROTOCOL.md)，該文件是兩個前端頁面與
後端之間的唯一介面規格，且與 `backend/protocol.py`、`frontend/src/protocol/types.ts`
三者必須一致。

主要功能需求摘要：

| 編號 | 需求 | 實作位置 |
|---|---|---|
| REQ-01 | 依固定 ROI 自影片抽幀，裁除病歷識別資訊 | `gateway.py` `extract_frames()` |
| REQ-02 | 對全片分類解剖部位（16 類 → 7 部位） | GNS 服務、`protocol.py` `REGION_MAP` |
| REQ-03 | 僅對**胃部 NBI**（排除食道）影像執行 IM 分割 | `gateway.py` `is_gim_candidate()` |
| REQ-04 | 僅對**胃部白光**影像執行息肉偵測與分割 | `gateway.py` `polyp_applies()` |
| REQ-05 | 疊圖一律以輪廓呈現，不遮蔽病灶內部黏膜 | `MaskBoundaryFilter.tsx` |
| REQ-06 | 部位與光源判讀須經時序平滑，不得逐幀跳動 | `lookup.ts` `buildRegionTrack` / `buildModalityTrack` |
| REQ-07 | IM 疊圖須經多幀共識確認後才顯示 | `lookup.ts` `gimFrameAt()` |
| REQ-08 | 所有影像與 mask 座標一律位於 ROI 像素座標系 | `PROTOCOL.md` §2 |

**安全相關需求**（對應 §7 的風險控制）：

| 編號 | 需求 |
|---|---|
| SAF-01 | 模型不得在其訓練定義域外輸出結果（見 REQ-03、REQ-04） |
| SAF-02 | 疊圖不得遮蔽判讀所依據的黏膜表面（見 REQ-05） |
| SAF-03 | 單幀的模型輸出不得直接呈現為發現（見 REQ-07） |
| SAF-04 | 掃描失敗必須明確回報，不得靜默停止 |

## 4. 架構設計（條款 5.3）

```
前端 (React)                        後端 (Python)
 /live  ─┐                   ┌── gateway :8080 ──┬── GNS   :8000  部位分類
         ├─ protocol/ ───────┤                   ├── GIM   :8001  IM 分割
 /report ┘  （唯一共享物）    └───────────────────┼── CGI   :8002  胃炎判別
                                                 └── POLYP :8003  息肉偵測+分割
```

- 五個模型的相依版本互斥（torch 1.11 / 2.0.1 三種環境），故**各自獨立行程**，
  以 HTTP 溝通。這是刻意的隔離設計，亦使單一模型失效不致污染其他模型。
- gateway 是唯一與前端溝通的元件，負責 session 生命週期、取樣排程與結果彙整。
- 兩個前端頁面**不得互相 import**，僅能透過 `frontend/src/protocol/` 溝通。

詳見 `README.md` 的「專案結構」與 `PROTOCOL.md` §1。

## 5. SOUP 清單（條款 8.1.2）

**SOUP = Software of Unknown Provenance。** 以下為本系統使用、但非本專案開發、
且未依 62304 流程驗證的軟體項目。版本為開發機上實測值。

### 5.1 AI 模型（含權重）

| 項目 | 版本／來源 | 用途 | 已知限制 |
|---|---|---|---|
| **GNS** (SGAFormer) | 研究團隊提供，`best_94.0050_AIGNS.pth` | 解剖部位分類 | 全片部位準確率約 80%（video1）／60%（video2）；G1–G6 對應到哪個部位論文未記載，現行對應表為經驗推得 |
| **GIM** (Mask2Former + FocalNet) | 研究團隊提供，`epoch_50_bd.pth` | IM 分割 | 僅於胃部 NBI 放大影像訓練；廣角觀察易漏判；逐幀輸出極不穩定（見 §7 HAZ-03） |
| **CGI** (GSCNet) | 研究團隊提供，`Paper_95.74_...pth` | 胃體為主胃炎判別 | 需三張特定部位白光影像；選圖策略由前端決定 |
| **YOLO (ultralytics)** | 本專案自行 fine-tune，`polyp_yolo.pt` | 息肉偵測 | **訓練資料僅 404 張獨立影像**，來自浙江大學另一台胃鏡主機；部署門檻 0.35 下召回 73%、誤報 12（見 §8） |
| **MedSAM** (vit_b) | bowang-lab/MedSAM，`medsam_vit_b.pth` | 息肉分割 | 通用醫學影像分割模型，**未針對胃息肉微調**；框錯了仍會產生看似合理的輪廓 |

> 上游偵測專案（kojix2/Gastric-polyps-detection）**未提供可用權重**，其 README 所附的
> 預訓練 ONNX 連結已失效（404），故偵測器係本專案以其標註資料自行訓練。

## 7. 風險管理（條款 7，介接 ISO 14971）

> 下表的「現況」欄位為**已實作並經量測驗證**的控制措施。量測數據取自 video1.mp4
> （14 分鐘完整診斷檢查，50,455 幀）與息肉驗證集（81 張未見過的影像）。

| 編號 | 危害 | 可能後果 | 風險控制措施 | 現況 |
|---|---|---|---|---|
| HAZ-01 | 模型在訓練定義域外輸出結果 | 對未經訓練的組織給出有把握的錯誤標註 | GIM 限胃部 NBI（排除食道）；息肉限胃部白光。**gateway 端強制**，不適用即回傳 null | 已實作（`is_gim_candidate` / `polyp_applies`） |
| HAZ-02 | 疊圖遮蔽病灶本身 | 遮蔽 pit pattern，妨礙判讀 | 一律只畫輪廓、中間不填色 | 已實作（`MaskBoundaryFilter`） |
| HAZ-03 | 單幀偽陽性被呈現為發現 | 誤導判讀 | 需最近 3 幀中 2 幀陽性才顯示；部位與光源均經時序平滑 | 已實作。實測：疊圖出現次數 30→16 次，去除的皆為單幀閃光 |
| HAZ-04 | 疊圖殘留於鏡頭已移開的黏膜 | 輪廓標在錯誤位置 | 停留時間限制為 0.5 秒 | 已實作（`IM_HOLD_S`）。**刻意不加長**：畫錯位置比短暫顯示更危險 |
| HAZ-05 | 息肉偽陰性 | 漏標病灶，延誤診斷 | 無有效控制措施 | **殘留風險**。部署門檻下召回 73%，且訓練資料與本院影像條件不同 |
| HAZ-06 | 覆蓋清單誤示「已檢查」 | 使用者誤以為該部位已充分觀察 | 以固定秒數為準（非比例），`unknown` 永不計入 | 已實作。**殘留風險**：停留時間不等於觀察品質 |
| HAZ-07 | 掃描靜默失敗 | 使用者以為分析完成，實為未完成 | 任一階段失敗即取消另一階段並回報 `failed` | 已實作（`asyncio.TaskGroup`） |
| HAZ-08 | 模型輸入前處理錯誤 | 模型於錯誤資料上推論，且無錯誤訊息 | 無自動偵測措施 | **殘留風險**。實例見 §8 |

**風險控制的驗證**：HAZ-01～04、HAZ-07 的控制措施均已於本機以真實檢查影片驗證，
量測數據記錄於對應的 commit message。HAZ-05、06、08 為**已接受的殘留風險**，
其可接受性建立在「醫師全程在場並自行判讀」的使用情境上。

## 8. 已知異常（條款 9）

62304 要求記錄已知異常。以下為開發過程中發現、已修復或仍存在的重要問題：

| 編號 | 問題 | 影響 | 狀態 |
|---|---|---|---|
| DEF-01 | 息肉偵測器接收 RGB，而 ultralytics 對 numpy 陣列預期 BGR | **偵測率降至 1/3**（89 個息肉中 65→19）。不報錯、框的位置仍正確，故長期未被發現 | 已修復 |
| DEF-02 | GIM 服務以同步 `def` 實作，多執行緒併發呼叫同一 mmseg 模型會靜默卡死（連 `/health` 都不回應） | 掃描永久停滯 | 已迴避（GIM 維持單一請求）。**根因未修**：若要提速應改為多行程而非多執行緒 |
| DEF-03 | `asyncio.gather` 於單一協程失敗時不會取消另一協程 | 掃描靜默卡在 `scanning`，例外被扣住不拋出 | 已修復（改用 `TaskGroup`） |
| DEF-04 | mask 形狀運算原以 CSS 像素為單位在瀏覽器執行 | 同一 mask 在 report 縮圖與 live 大畫面上形狀不一致 | 已修復（移至後端，以 ROI 像素運算） |
| DEF-05 | 部位已平滑而光源未平滑 | 疊圖適用性判定全片跳動 324 次 | 已修復（降至 38 次） |

> DEF-01 與 DEF-02 都是**不會產生錯誤訊息的失效**。這類問題正是 §9 測試缺口
> 最需要涵蓋的類型。

## 9. 驗證與測試（條款 5.5–5.7）— **主要缺口**

**現況：本專案無任何自動化測試。** 所有驗證均為人工執行，證據散見於 commit message。

這是相對 62304 Class B 要求最明顯的落差。Class B 要求：

| 條款 | 要求 | 現況 |
|---|---|---|
| 5.5.5 | 軟體單元驗證 | **未建立** |
| 5.6 | 軟體整合與整合測試 | **未建立**（有人工端到端驗證，無自動化、無紀錄保存） |
| 5.7 | 軟體系統測試 | **未建立** |
| 5.1.6 | 驗證的可追溯性 | **未建立** |

**已執行的人工驗證**（可作為日後自動化的基礎）：

- 契約不變式：掃描完成後每幀皆有 `gns`；NBI 幀皆有 `gim`；白光幀無 `gim`
- 座標一致性：mask 與 ROI 尺寸相符，疊圖對齊
- 適用範圍：NBI 幀拒絕息肉推論、白光幀拒絕 IM 推論
- 效能：完整掃描 14 分鐘影片（50,455 幀）耗時 567 秒
- 息肉偵測器：於 81 張未見過的影像上量測召回與誤報

**建議優先建立的測試**（依風險排序）：

1. `protocol` 三份定義（TS／Python／文件）的一致性測試 — 防止契約漂移
2. `is_gim_candidate` / `polyp_applies` 的適用範圍測試 — 直接對應 HAZ-01
3. 模型服務的前處理測試（含通道順序）— 直接對應 DEF-01 這類靜默失效
4. 掃描的契約不變式測試 — 上述人工檢查的自動化
